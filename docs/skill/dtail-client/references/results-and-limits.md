# Interactive control, results, and limits

## Reload a live session

Add `--interactive-query` to `dcat`, `dgrep`, `dtail`, or `dmap` when a controlling TTY exists; `dtail` does it by default when stdin and stdout are a terminal (`--no-interactive` turns it off), never in a pipe or script. The TTY accepts `:show`, `:help` (with per-mode examples), `:reload <flags>`, `:query [query]` (`dtail`, `dmap`), `:tail [regex]` (`dtail`), `:fields [table]`, `:probe`, and `:quit`. `:query <query>` switches a `dtail` session from following lines to that query (or replaces it; in `dmap` it replaces the query), `:tail` switches back to the regex followed before, `:tail <regex>` to another regex, all on the same session; the query or regex is the rest of the line, unquoted (no shell quoting), `:query` alone shows the running query, and `:show` prints `workload=query` or the mode; an empty line pauses or resumes the output. On a terminal, Tab completes commands, flags and the current filter/query/files value, inside a `--query` the query language and the probed tables/fields, inside `--files` remote paths, Up/Down recall earlier lines, Alt-E (or Alt-V) opens the line in `$VISUAL`/`$EDITOR` and puts the saved text back on the line to be entered, `--edit-mode vi` (or `Client.EditMode: "vi"`) adds a vi normal mode after Esc (motions, `d`/`c`/`y`, `D`, `u`, `k`/`j` history), and typing a command pauses the output until it is entered (a hint line says so); `:help` and `:fields` keep the output paused until the next empty line, and a line started while paused shows the prompt `dtail> `.

- **Field discovery.** An interactive session probes up to 3 servers in the background (at start, after every applied `:reload`, every 60 s while the output runs) for the MapReduce tables, fields, `$variables` and sample values of a bounded sample of the files being read. The answer lists every table of the sampled window (also of lines beyond the 500 kept) and, per table, the `$variables` its lines carry. `:fields` prints that catalog, from the answers about the current files only (a table name, matched ignoring case, narrows it to that table and its `$variables`, after a **table probe**: the servers search up to 4 MiB of each file's end for that table's lines only, so a table that logs rarely gets fields too; waited for up to 2 s, repeated at most once a minute); `:probe` probes now and reports which servers answered. Non-interactive clients never probe.
- **Query completion.** Tab after `:query ` or inside a `:reload --query '...'` value completes the query language (clause keywords, aggregations, operators, set functions, log formats) and the probed tables, fields, `$variables` and sample values. It is guided, one step per Tab: `from` -> table -> `select` -> items -> `where` -> `group by` -> `order by` -> `limit` (formats without tables start at `select`), a single next step is inserted directly, clauses already in the query are not offered again, after a finished item only the next clauses (and `and` after a where condition) are listed with a hint that a comma adds another item, a value position offers only sample values, and the rare clauses `set`, `interval`, `outfile`, `logformat`, `rorder` complete only when typed. Once the query names a table (anywhere in the line), fields, `$variables` and values come only from that table's lines; any clause order still completes when typed by hand. A listing starts with a heading of what is expected (`select item`, `field to count`, `value for x`), then the candidates as bare names in labelled groups, one per line (`aggregation:`, `field:`, `variable:`, `next:`; fields before `$variables`), wrapped to the terminal and cut after three rows with `... (N more, type to narrow)`; the `(`, `)`, quotes and blank are added only on insert (no blank after the `)` of `count(field)`, so a comma for another item can follow; Tab right after the `)` lists the next clauses with the comma hint, inserting the blank only at the end of the query). It waits for a server only once a `from TABLE` is typed and that table was not probed on its own within the last minute: then it asks for a table probe and waits up to 1 s with the output running (only that Tab; later ones complete from the cache with a hint, and a probe no server answered is retried after 5 s). Before the first probe answer only the language completes (a hint says so).
- **Path completion.** Tab inside `:reload --files` completes the last comma-separated entry from a listing of the remote directory (cached 2 minutes, 5 s when the server answered `probe: timed out` or could not list the journal units; the current files' directories are prefetched at session start, after `:reload` and on `:probe`, otherwise fetched with a wait of at most 1 s during which the output runs). The listing comes from the first server that is up. Files are offered only if the user's `readfiles` permissions allow them; directories on an approximation of the rules that can reveal some directory names; hidden names only after a typed `.`; names with commas, edge blanks or control/format characters are skipped; `journal:` prefixes complete unit names (listed on Tab only, never prefetched; dserver keeps the unit list for a minute). A server with `Server.PathCompletionDisable: true` answers no listing.
- **Colors.** With terminal colors the control output, `:help`, `:show`, `:fields`, the prompt and the candidate lists are colored, and queries are highlighted (in `:show`, in the `query: ...` line echoed after an applied query reload, and above `dmap`/`dtail --query` result tables). The result-table highlighting applies outside interactive mode too, but only when stdout is a terminal and no payload goes to a log file; piped output (`dmap ... > out`) gets the query in one color as contiguous text, so `grep` finds it. `--noColor`, `--plain` or `Client.TermColorsEnable: false` turns all of it off, and a control TTY that is no terminal is never colored; styles live in `Client.TermColors.Interactive`.

Client and every server must speak protocol 5; the initial workload starts with `SESSION START` (no fallback), and a rejected reload leaves the current workload running. A successful reload reuses SSH sessions and drops late output from the prior workload. A reload updates the servers whose session is up, all or nothing; servers that are down or still connecting do not block it (the reload answer names them, a connecting one and a `dtail` reconnect start with the new workload); `:show` reports `servers=` and active `sessions=`. An interactive `dtail` holds both workloads on one client: its running session can switch between following lines and a MapReduce query, both ways, with a `SESSION UPDATE` (no reconnect); query results are reported only while a query runs, and once more when the session goes back to following lines (with an outfile always written; without one printed only if it has rows and differs from the table printed last, covering only what arrived since the last report; it can lack up to one query interval), and following lines restores the regex, `--invert`, context and `--max` it had before the query.

`:reload` accepts `--files`, `--plain`, `--quiet`, and `--timeout` for all modes. `dgrep` and grep-driven `dtail` also accept `--grep`/`--regex`, `--invert`, `--before`, `--after`, and `--max`; `dmap` and query-driven `dtail` accept `--query`. Flags omitted on reload retain their values. `--invert=false` clears a previous inversion. Each reload needs at least one flag and must retain nonblank files and, in query mode, a nonblank query. An empty `--regex ''` selects every line in a reload unless inversion remains on; `:reload --grep ''` is rejected. Quote a path or regex with spaces as on a shell command line; reload tokenization does not expand variables, commands, or globs. See `doc/interactive-query.md` for its exact quoting rules.

## Interpret output and status

- Standard remote output prefixes lines with source information such as `REMOTE|host|...`; `--plain` emits payload without that framing. `--noColor` suppresses terminal color. dserver marks its control messages, so payload lines like `.syn close connection` or `AUTHKEY OK` stay intact in plain mode; client and dserver must both speak protocol 5 and be upgraded together. Against an older dserver a protocol 5 client reports `unsupported DTail server: not a protocol 5 server` and fails that connection (`dcat`/`dgrep` exit `1`); an older (4.x or earlier) data client talking to a protocol 5 dserver gets a version mismatch error and its session stays open until the client is stopped or the server's idle timeout ends it, so a one-shot `dcat` waits instead of exiting (a 4.x `dtailhealth` gets its session ended at once and fails its check); a client of any other version (a future one, another 5.x) gets its session ended without the close handshake.
- Default `fout` logging sends payload to stdout and writes diagnostics to `~/log/YYYYMMDD.log`; it does **not** copy payload into that file. `--log-payload` or `Client.LogPayload` opts in to the copy. `--logger stdout` uses stdout only, `--logger none` disables the logger, and `--logger file` uses a file sink, including payload. Explicit `--logger`/`--logDir` beats `Common.Logger`/`Common.LogDir`, which beat command defaults. In server mode, dserver warnings appear in client output even at a restrictive client log level; with `--plain`, a `WARN|...` line can be mixed into redirected payload. Serverless warnings use the client's logger and are filtered by its log level (default `warn`).
- `dcat` and `dgrep`: `0` means the sessions completed (including a `dgrep` search with no match); `1` means connection, setup, unsupported capability (`journal-v1`) or protocol version, or truncated-session failure; `2` means an invalid flag or a server-reported command failure such as missing/denied/unreadable input, glob cap, malformed read, or output-buffer overflow. The highest status among servers wins. Partial output can precede a nonzero status.
- `dtail` follows and reconnects, so its status does not signal every failed read. `dmap` may write the received partial result and exit `0` after a reported incomplete result or interrupted session; check its WARN diagnostics before treating its outfile as complete. Scheduled and continuous MapReduce jobs have separate failure behavior described in `doc/server-configuration.md`. `dtailhealth` prints `OK` (`0`), `WARNING` (`1`, including serverless mode), or `CRITICAL` (`2`).

## Compatibility and source boundaries

- Remote `journal:` reads require `journal-v1`. Remote paths with interior spaces or a `base64%` prefix need no capability. A reload to a `journal:` target checks all active servers before changing any of them. Source paths containing commas or leading/trailing blanks cannot be represented by `--files`.
- A remote file or journal target is checked against dserver permissions and OS access. A missing path, empty glob, or capped glob can make a result incomplete. Long lines may be split at `Server.MaxLineLength` with a warning. Compression support depends on the dserver build.
- For a result intended to be machine-readable, use `--plain --logger stdout` and still account for server warnings and exit status. When exact bytes matter, verify the data stream and source conditions; `dcat --plain` in serverless mode can reproduce a regular file, while server-mode warnings can enter stdout.
